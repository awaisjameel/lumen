# Phase 11 audit and local repair

Date: 10 October 2026. This record follows
[the Phase 11 record](phase11-compression-2026-10-09.md) and corrects it where
the two differ.

## Audit summary

Audited `feat/phase-11-lossless-compression` at `5564664` against `main`:
95 changed files, 6,139 additions and 124 deletions. The working tree was
clean; the repairs below are unstaged.

The audit traced a compression run from the grid, viewer and inspector
commands through the bridge, `CompressionService`, the coordinator, the codec
subprocesses and verifiers, the publisher, the journal in SQLite and the
annotation transfer, then back through history, restoration and recovery at
start-up. It also covered the JPEG XL decoding that replaced FFmpeg's, the
dependency and notices scripts, and the native acceptance suite.

The branch passed its own gates. The defects below were found by reading and
by probes written for each suspicion.

## Findings

| Finding | Original behaviour | Local repair |
| --- | --- | --- |
| Destination folder lease | `LeaseCopyFolders` opened each folder for attributes only. Windows applies a share mode only to a handle that reads, writes or deletes, so the folder a copy is published into could be renamed or removed while "leased"; only its ancestors were held, by their open children. A probe renamed it from another process. The record's claim that leases refuse junction substitution did not hold for the folder itself. | Folders are opened for listing, which the share mode governs. A regression renames and removes the leased folder itself. |
| Decoder output bound | `cappedBuffer` embedded `bytes.Buffer`. `os/exec` copies output with `io.Copy`, which used the embedded `ReadFrom` and never called the capped `Write`: the 64 MiB bound on a decoder's PNG, the render worker's output and FFprobe's report bounded nothing. A probe received 87 MB through it. | The buffer is a field. A regression copies through `io.Copy` on both sides of the bound. |
| Large JPEG XL | With the bound real, a JPEG XL whose PNG exceeds it (about 22 megapixels of photograph and up) would have no thumbnail or viewing copy; FFmpeg read every size before this phase. | Over the bound, FFmpeg decodes at the size asked for, as before Phase 11: upright, taken for sRGB. The inspector shows such a file without its profile. Every copy Lumen itself writes (16 megapixels at most) stays on the exact path. |
| Start-up | `ServiceStartup` returned the journal's recovery error, and Wails stops the application on one: an interrupted run whose row could not be settled (a foreign candidate path, a folder that became a junction, a drive not ready) kept the whole library from opening, at every launch. Recovery also stopped at the first such row, and a failed attempt was never made again in that session. | Start-up logs and continues. Every row is tried and the failures are returned together. Compression refuses new work while a row is unsettled and tries again on the next request. |
| A block applied while a file waits its turn | The wait for the indexer's politeness can last hours. A block arriving meanwhile cancelled the wait, and the error ended the whole run as failed; once encoding had started, the same block left the file "planned: interrupted" in a run reported as finished. | That file fails with "not visible" and the run goes on to its other files. A lookup that merely fails no longer counts as a block. |
| Candidates never discarded | History returns the newest 100 runs, but older runs and the candidate files of reviews never saved or cancelled were kept for good, with no screen left to discard them from. | At start-up, runs beyond the 100 are removed with their candidates. A run with a publication still to settle is kept whatever its age. History and pruning share one bound. |
| Extension of a registered copy | The copy's asset stored its extension as written in the file name; the scanner stores lower case. | Lower case, as a scanned file's. |
| Restoration timeout | Reconstructing a JPEG ran the decoder with no time limit, unlike every encoder. | Restoration runs through the codec with the ordinary limit. |
| One job read by loading the run | Reveal and Restore loaded every visible outcome of a run (up to 10,000) to find one. | One visible row is read by its id. |
| Eligibility written twice | The plan's format rules repeated the catalogue's capabilities by hand. | The plan asks `core.CompressionSupported`. The `Capabilities` service method and its bridge function, which nothing called, are removed. |
| Idle polling | The open tools page ran the history query twice a second for as long as it was shown. | It polls only while a run is working; each of the user's actions already reloads. |
| Minimum saving field | Clearing the field sent an empty string for an integer, and an out-of-range number was refused as an invalid plan. | The field takes a whole percentage within the engine's bounds and shows what it took. |
| Unnamed bounds | 100, 10,000 and 90 were literals in Go, SQL and the view. | Constants in `core`, mirrored in the bridge and held by the contract test. |

## Corrections to the Phase 11 record

- "Destination ancestor leases refuse rename/junction substitution" is true of
  the destination folder too only from this repair.
- "PNG output is capped at 64 MiB" is enforced only from this repair, and a
  larger picture is then read by FFmpeg rather than refused.
- History is the newest 100 runs, and that is also all that is kept.
- Native compression acceptance is 41 checks; the suite now opens the tools
  page afresh before reading a run planned through the service, since the
  page no longer polls while idle.

## Limits that remain, for the owner

- **16 megapixels.** JPEG and PNG sources above 16 million pixels are skipped
  as unsupported. That excludes the common 24-megapixel camera JPEG and
  48-megapixel phone photo. The bound exists for the PNG verifier, which holds
  two decoded pictures in memory; the JPEG paths compare files and decoded
  PPMs on disk and could take a higher bound once encoder memory at those
  sizes is measured against the 512 MiB limit. Raising it is a product
  decision with a benchmark, not a repair.
- A JPEG XL over the decoder bound is shown without its colour profile.
- Clean-VM installer execution, signing and a camera-photo matrix remain
  outside local acceptance, as the Phase 11 record says.
